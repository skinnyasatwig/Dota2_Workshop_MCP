# Dota map automation capabilities

This is the plain-language answer to “what can the MCP do without Hammer now?”

| Capability | Status | What it means | Remaining limit |
|---|---|---|---|
| Engine readiness diagnosis | Ready and demonstrated | `map_engine_readiness_probe` performs one command-free diagnostic launch, records game-state transitions, console evidence, dialogs, and a screenshot, then always shuts down. It can instead restore, focus, attach to, and preserve a user-started tools session. Fresh request IDs prevent replayed console history from masquerading as readiness. | The probe deliberately sends no corrective gameplay command, so it may report a dashboard state that the navigation runner can now resolve automatically. Historical direct-renderer NVIDIA failures remain machine-specific evidence. |
| One map specification | Ready | Build, terrain, sync, preview, validation, and engine-route tools read the same checked JSON contract. | A malformed or ambiguous contract is rejected instead of guessed. |
| Terrain generation | Ready | Rectangles, circles, rings, paths, polygons, named regions, water, height, tilesets, cliffs, and ramps can be generated repeatably. | Freeform decorative meshes, true holes, irregular arches, and curved world geometry still need Hammer or more Valve-format research. |
| Reuse and symmetry | Ready | Regions, paths, and whole components can be mirrored and placed repeatedly with automatic name isolation. | Visual composition still needs a human eye. |
| Safe writes | Ready | Dry-run reports, staging, backups, transactional replacement, and rollback protect source and compiled maps. | Git remains the long-term history; transaction backups are short-term recovery. |
| Material preflight | Ready for all VMAP `.vmat` references | Build and contract-sync previews resolve every serialized material against addon/base loose content, compiled assets, and addon/Dota/core VPKs. Writes refuse missing or unsafe resources; `map_compile` stops before ResourceCompiler; `map_validate` can require compiled readiness. The current 3v3 map resolves all 10 references (2 unique materials) with zero findings. | Existence does not prove artistic suitability, shader correctness, texture quality, or runtime appearance; those still need compiler/visual evidence. |
| Checked solid volumes | Ready for boxes and flat/sloped convex volumes | Camp bounds, general/hero/Dota triggers, boss-attack areas, no-ward zones, and player blockers can use boxes or three- to 64-sided convex footprints. A footprint may provide coplanar bottom/top corner heights for a safe sloped solid. Generation, exact drift repair, mirroring, preview, and offline blocking follow the real shape. Valve's converter and compiler are both tested. | Arbitrary classes, concave footprints, twisted faces, truly curved solids, and general world meshes are rejected; base/FoW point blockers use separate Valve entities. |
| Checked world solids | Ready for flat or per-corner-sloped convex/concave extrusions and composite rectangular arches | `managedSolids` turns one validated simple outline into a named, always-solid `func_brush`. The MCP keeps heights attached through mirroring, deterministically triangulates top/bottom faces, closes the sides, rejects open/non-manifold topology, detects drift, previews the true shape and uphill direction, and blocks the true concave footprint and vertical standing corridor offline. A reusable `arch` composes two posts and an elevated lintel without exposing arbitrary mesh editing. Valve's converter and compiler accepted the L-shaped and arch fixtures. | One outline cannot contain holes. Curves, irregular arches, arbitrary triangle soups, moving geometry, and decorative material composition remain unsupported. The 256-unit offline agent height is a conservative check, not proof of Valve GridNav overhead behavior. |

Preview outlines the surfaces and reports conservative terrain clearance. Valve accepted the complete visible composition. In a causal engine fixture with tile terrain 46,341 units away and visible solids omitted, the three navigation surfaces created a 2,048-unit route while a nearby no-surface control was non-traversable. | GridNav aliases different heights at the same X/Y to a zero-length route, so independent stacked bridge and underpass routes cannot be claimed through this API. Each real map still needs route validation. Decorative bridge art remains separate. |
| Checked point blockers | Ready from official definitions | Team-aware `npc_dota_base_blocker` entities and explicitly linked `ent_fow_blocker_node` chains have reusable builders, validation, and preview lines. | Their final team collision and fog behavior remain targeted engine facts not covered by the route acceptance run. |

A bridge expands into a visible deck/navigation pair, and an approach derives its slope from two endpoints. | Decorative wall/bridge meshes, sloped wall runs, curved/irregular arches, choosing project-specific approach placement, attackable-area design, and final visual dressing still need explicit design, GridNav evidence, or Hammer. |

The doctor/catalog compare installed metadata plus five authoritative hashes to the proven baseline. `map_recipe_refresh_report` identifies affected families, prepares a candidate, and requires build, unit/integration, smoke, compiler-fixture, and acceptance-map evidence. ## What “minimal Hammer interaction” means

Most layout iteration can now happen in JSON plus generated previews. Simple flat or sloped convex/concave world solids, rectangular arches, and checked bridge decks/approaches no longer require Hammer. Hammer is still the right tool for final visual dressing, freeform mesh sculpting, and visual inspection. The goal is not to pretend Hammer no longer exists; it is to reserve Hammer for the parts only Hammer can reliably judge.
