# Dota map automation capabilities

This is the plain-language answer to “what can the MCP do without Hammer now?”

| Capability | Status | What it means | Remaining limit |
|---|---|---|---|
| Engine readiness diagnosis | Ready and demonstrated | `map_engine_readiness_probe` performs one command-free diagnostic launch, records game-state transitions, console evidence, dialogs, and a screenshot, then always shuts down. It can instead restore, focus, attach to, and preserve a user-started tools session. Fresh request IDs prevent replayed console history from masquerading as readiness. | On this PC, direct automation still hits NVIDIA `NVAPI_ACCESS_DENIED` after a checked profile reset, while Steam did not forward `-applaunch`; the normally launched attach path is proven. |
| One map specification | Ready | Build, terrain, sync, preview, validation, and engine-route tools read the same checked JSON contract. | A malformed or ambiguous contract is rejected instead of guessed. |
| Terrain generation | Ready | Rectangles, circles, rings, paths, polygons, named regions, water, height, tilesets, cliffs, and ramps can be generated repeatably. | General decorative, sloped, or concave Source 2 meshes still need Hammer or more Valve-format research. |
| Reuse and symmetry | Ready | Regions, paths, and whole components can be mirrored and placed repeatedly with automatic name isolation. | Visual composition still needs a human eye. |
| Safe writes | Ready | Dry-run reports, staging, backups, transactional replacement, and rollback protect source and compiled maps. | Git remains the long-term history; transaction backups are short-term recovery. |
| Checked solid volumes | Ready for boxes and convex prisms | Camp bounds, general/hero/Dota triggers, boss-attack areas, no-ward zones, and player blockers can use boxes or three- to 64-sided convex footprints. Generation, exact drift repair, mirroring, preview, and offline blocking follow the real shape. Valve's converter and compiler are both tested. | Arbitrary classes, concave footprints, sloped faces, and truly curved solids are rejected; base/FoW point blockers use separate Valve entities. |
| Checked point blockers | Ready from official definitions | Team-aware `npc_dota_base_blocker` entities and explicitly linked `ent_fow_blocker_node` chains have reusable builders, validation, and preview lines. | Their final team collision and fog behavior remain targeted engine facts not covered by the route acceptance run. |
| Diagnostic preview | Ready | A top-down image shows terrain, contours, cliffs, ramps, water/currents, paths, entities, tower ranges, camps, objectives, minimap bounds, checked volumes, holes, unreachable areas, bright-cyan exact convex PHYS outlines, medium-cyan mesh envelopes, muted-cyan bounds fallbacks, approximated obstruction circles, and unresolved props. | It is a diagnostic drawing, not the final in-game rendering. |
| Offline reachability | Ready for static Rubikon PHYS families | The tile grid can find holes, trapped spawns, isolated land, blocked entrances, inaccessible objectives, bad path segments, and checked player-blocker footprints without launching Dota. Collision-enabled props are inspected through VRF in shadowing order: loose compiled addon model, packed addon `pak01_dir.vpk`, then base Dota VPK. Per-part bind poses are applied; convex `RnHull_t` vertices produce exact top-down outlines, mesh vertices produce conservative convex envelopes, and sphere/capsule bounds remain conservative. Entity pitch/yaw/roll and scale are then applied. Render and hitbox bounds are never substituted. | Concave mesh details and curved sphere/capsule outlines are broader than their exact surfaces. Exact trees, dynamic collision, team-selective blockers, and Valve's compiled navigation remain engine facts. |
| Real Dota navigation | Ready and demonstrated | `map_engine_nav_test` compiles and performs one guarded launch, or restores and attaches to a running tools session. DebugSDK 1.1.3 uses compact correlated commands, chunks long routes below Source 2's console limit, and reassembles endpoint, segment, traversability, and path-length results. The 3v3 acceptance run returned all 4 routes and 64 checks. | Automatic startup remains blocked on this PC, so the proven path begins with one normal Workshop Tools launch. The current map has 8 genuine blocked checks around four non-traversable mirrored waypoints. |
| Reusable Dota structures | Ready, including boss no-ward solids | Bases, Ancients, towers, fountains, shops, camps, boss pits, player starts, and gates have checked builders and stock names. Camps can create spawn boundaries; boss pits can create compiled regular-polygon no-ward volumes. | Bespoke concave walls, attackable-area design, and final visual dressing still need explicit design or Hammer. |
| Valve recipe library and safe refresh | Ready and evidence-gated | Terrain cores, cliff/ramp patterns, volume topology, point blockers, and Valve prefab references are catalogued. The doctor/catalog compare installed metadata plus five authoritative hashes to the proven baseline. `map_recipe_refresh_report` identifies affected families, prepares a candidate, and requires build, unit/integration, smoke, compiler-fixture, and acceptance-map evidence. The CLI safely runs the four non-engine checks. | The MCP deliberately cannot record or auto-bless a new baseline; a maintainer must review passing evidence and commit the candidate separately. |
| Entity validation | Ready for official FGD semantics | Known classes, inherited properties, basic types, dropdown choices, explicit numeric bounds, and resolvable named-entity links are checked against installed Valve definitions. The entity catalog exposes the same useful constraints before generation. | Runtime-only behavior, dynamic/wildcard targets, and undocumented custom metadata cannot be proven by FGD files. |
| Automated verification | Ready | The TypeScript build, unit/integration tests, MCP smoke suite, real 3v3 contract sync, preview, reachability, FGD checks, compile, attached readiness, and real GridNav checks are reproducible. | Final visuals need human judgment; correcting the 3v3 map's four non-traversable mirrored waypoints is a separate map milestone. |
| Repository compile fixture | Ready and demonstrated | `npm run test:compiler-fixture` applies a checked-in MCP-authored entity/volume payload to Valve's locally installed blank map, round-trips it through `dmxconvert`, compiles a real VPK, and removes the isolated temporary addon. It uses no private 3v3 files and copies no Valve VMAP into Git. | The opt-in proof requires a Windows machine with Dota Workshop Tools; ordinary unit tests remain engine-free. |

## What “minimal Hammer interaction” means

Most layout iteration can now happen in JSON plus generated previews. Hammer is still the right tool for final visual dressing, arbitrary/concave/sloped mesh sculpting, and visual inspection. The goal is not to pretend Hammer no longer exists; it is to reserve Hammer for the parts only Hammer can reliably judge.
